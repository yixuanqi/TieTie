### 性能测试场景及结果

使用 Linux headless Chromium（**不是 Windows WebView2**），模拟 Rust IPC 返回 500 条记录，其中 100 条图片，历史界面一次最多渲染 250 条（其内含 50 张图片）。

| 项目 | 结果 |
| --- | --- |
| 初始展示卡片数 | 250 |
| 历史中初始缩略图读取次数 | 50 |
| 连续 40 次 `notes-changed`（没有更新历史结果）后是否复用第一个卡片 | 是 |
| 连续 40 次事件后是否复用第一张图片节点 | 是 |
| 仅变更一张卡片时是否复用第一张图片节点 | 是 |
| 上述测试中图片 IPC 总读取次数 | 50（未增加） |
| 连续 20 次关键词变化的同步 DOM 更新平均耗时 | 单次约 12 ms（仅本机模拟值） |
| JS 异常 | 0 |

**说明**：这些数值不能外推为真实 Windows 安装包的帧率、FPS、CPU、GPU、内存或磁盘响应。试验也没有覆盖真实 PNG 的编码/解码耗时，仅验证前端减少了不必要的 DOM/图片重建。

## 优化内容

1. 历史卡片采用 keyed DOM 复用；数据签名不变时不做 DOM 更新。
2. 首次生成磁盘缓存缩略图（192×144 上限），历史列表不再取全分辨率原图。
3. 独立浮贴只因自身文本、Todo、图片或视觉状态改变重绘；跨卡片变更不影响它。
4. 移除透明 WebView2 背后的 `backdrop-filter`，主面板改为实色暖纸白，以降低桌面内容透字与合成问题。浮贴仍可半透明。

## 用户 Windows 上需要补做的验证

- 比较 `npm run dev` 的 Debug 与 `npm run build` 的 Release，观察是否还有闪烁。
- 首次打开历史页、连续上下滚动、切换标签、打开 3–5 张独立浮贴、勾选 Todo，以及拖动/缩放浮贴分别录屏。
- Windows 任务管理器中查看 `贴贴`、`msedgewebview2.exe` 对应的 CPU / 内存，重点关注多浮贴时的增长。
- 记录 Windows 版本、WebView2 Runtime 版本、显示缩放比（100%/125%/150%）。

仍然存在的风险：JSON 全量保存、全量原始图加载到单张浮贴，以及 Windows 透明窗体/WebView2/显卡驱动的合成差异。后续数据存储方案需要重点处理 SQLite、持久化索引和缩略图生命周期。
